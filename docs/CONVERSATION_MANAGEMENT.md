# Conversation Management

## 1. Conversation Lifecycle

Each conversation is a named, persistent thread of messages between an authenticated user and the HRMS AI Assistant. Conversations are owned exclusively by the user who created them.

```
  POST /api/v1/chat              ← creates a new conversation (no conversation_id)
         │
         ▼
  Conversation created with:
    - UUID id
    - owner: user_id from JWT
    - title: auto-generated from first message
    - created_at / updated_at timestamps

  POST /api/v1/chat              ← continues an existing conversation
  Body: { "conversation_id": "<uuid>" }
         │
         ▼
  Messages appended; updated_at refreshed

  GET /api/v1/chat/conversations            ← list all conversations
  GET /api/v1/chat/conversations/{id}       ← inspect one conversation
  GET /api/v1/chat/conversations/{id}/messages  ← paginated message history
  DELETE /api/v1/chat/conversations/{id}    ← permanent deletion
```

---

## 2. Message Types

Each message stored in a conversation has a `role` field:

| Role | Description |
|------|-------------|
| `user` | Message submitted by the authenticated employee |
| `assistant` | Response generated by the LLM |
| `tool` | Tool call invocation request from the LLM (stored with tool name and args) |
| `tool_result` | Result returned by the tool executor after calling an HRMS or RAG service |

Tool messages and tool_result messages are stored to allow full context reconstruction for multi-turn conversations, but are filtered from user-facing message list responses to keep them clean.

---

## 3. Conversation Ownership & Isolation

> [!IMPORTANT]
> Every conversation is strictly isolated to its owner. Cross-user access is blocked at the repository layer, not the route layer.

- **Creation**: The `user_id` for a new conversation is taken exclusively from `principal.user_id` (the verified JWT subject). The client cannot specify a different owner.
- **Read / Delete access**: `ConversationRepository` queries always include a `user_id` predicate. A user requesting another user's conversation ID receives `404 Not Found` (not `403`), preventing ID enumeration.
- **No admin override**: Even `admin`-role users cannot read or delete another user's conversations via the standard API (admin tooling would require a separate privileged endpoint).

---

## 4. Context Window Management — Sliding Window

Storing many messages in a conversation does not mean all of them are sent to Ollama on every request. `PromptBuilder.build_history_window()` applies a sliding window strategy:

1. Retrieve the last `N` message pairs (default `CHAT_MAX_HISTORY_TURNS=10`) from the conversation.
2. Always include the **system prompt** at position 0 (injecting verified identity).
3. Append the windowed history turns.
4. Append the current user message at the end.

**Why sliding window?**
- Keeps token usage bounded within `CHAT_CONTEXT_LENGTH` (default 4096 tokens).
- Prevents context overflow for long-running conversations.
- The full message history is always preserved in SQLite; only the LLM prompt is windowed.

---

## 5. What Is and Isn't Stored

### Stored in SQLite

| Stored | Notes |
|--------|-------|
| `user` messages | Verbatim user input (after length validation) |
| `assistant` messages | LLM-generated response text |
| `tool` call records | Tool name, arguments JSON |
| `tool_result` records | Tool execution result JSON |
| Conversation metadata | id, user_id, title, timestamps |

### Never Stored

| Not Stored | Reason |
|-----------|--------|
| JWT access tokens | Bearer tokens have a TTL and are never persisted |
| Passwords or password hashes | Only stored in the `users` table (never in messages) |
| Raw embedding vectors | Stored in Qdrant, not in conversation history |
| Ollama thinking tokens | Internal model reasoning traces are dropped before storage |

## 6. Listing and Deleting Conversations via API

### List All Conversations

```powershell
$headers = @{Authorization="Bearer $token"}
$convs = Invoke-RestMethod -Uri http://127.0.0.1:8000/api/v1/chat/conversations -Method GET -Headers $headers
$convs.conversations | Format-Table id, title, message_count, updated_at
```

**Response schema**:
```json
{
  "conversations": [
    {
      "id": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
      "title": "Leave balance inquiry",
      "created_at": "2026-11-17T05:00:00Z",
      "updated_at": "2026-11-17T05:01:30Z",
      "message_count": 4
    }
  ],
  "total": 1
}
```

### Get Messages for a Conversation

```powershell
$id = "3fa85f64-5717-4562-b3fc-2c963f66afa6"
$msgs = Invoke-RestMethod -Uri "http://127.0.0.1:8000/api/v1/chat/conversations/$id/messages" -Method GET -Headers $headers
$msgs.messages | Format-Table role, content, created_at
```

**Response schema**:
```json
{
  "conversation_id": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
  "messages": [
    {
      "id": 1,
      "role": "user",
      "content": "What is my leave balance?",
      "created_at": "2026-11-17T05:00:00Z",
      "tool_name": null
    },
    {
      "id": 2,
      "role": "assistant",
      "content": "Your current annual leave balance for 2026 is 12 days...",
      "created_at": "2026-11-17T05:00:02Z",
      "tool_name": null
    }
  ],
  "total": 2
}
```

### Delete a Conversation

```powershell
$id = "3fa85f64-5717-4562-b3fc-2c963f66afa6"
Invoke-RestMethod -Uri "http://127.0.0.1:8000/api/v1/chat/conversations/$id" -Method DELETE -Headers $headers
```

Returns `204 No Content` on success, `404 Not Found` if the conversation does not exist or belongs to another user.

## 7. Database Schema Reference

### `conversations` table

| Column | Type | Description |
|--------|------|-------------|
| `id` | TEXT (UUID) | Primary key, auto-generated |
| `user_id` | TEXT | Owner's user UUID (from JWT `sub` claim) |
| `title` | TEXT | Auto-generated title (first message truncated to 60 chars) |
| `created_at` | TEXT | ISO 8601 UTC timestamp |
| `updated_at` | TEXT | ISO 8601 UTC timestamp (updated on every new message) |

### `messages` table

| Column | Type | Description |
|--------|------|-------------|
| `id` | INTEGER | Auto-increment primary key |
| `conversation_id` | TEXT (FK) | References `conversations.id` (CASCADE DELETE) |
| `user_id` | TEXT | Message owner — redundant index for fast per-user queries |
| `role` | TEXT | `user`, `assistant`, `tool`, `tool_result` |
| `content` | TEXT | Message text content |
| `tool_call_id` | TEXT (nullable) | Links tool result back to its tool call |
| `tool_name` | TEXT (nullable) | Name of the tool that was invoked |
| `metadata_json` | TEXT (nullable) | JSON-encoded tool arguments or result metadata |
| `created_at` | TEXT | ISO 8601 UTC timestamp |

> [!NOTE]
> The `tool_call_id`, `tool_name`, and `metadata_json` columns were added in Phase 5 via an idempotent `ALTER TABLE` migration that runs at application startup. The migration uses `IF NOT EXISTS` semantics and is safe to run multiple times.

## 8. Example PowerShell API Workflow

```powershell
# Authenticate
$loginBody = '{"email":"alice@novatech.com","password":"securePass123"}'
$login = Invoke-RestMethod -Uri http://127.0.0.1:8000/api/v1/auth/login -Method POST -Body $loginBody -ContentType application/json
$token = $login.access_token
$headers = @{Authorization="Bearer $token"}

# Start a new conversation
$chatBody = '{"message":"What is my leave balance?"}'
$chat = Invoke-RestMethod -Uri http://127.0.0.1:8000/api/v1/chat -Method POST -Headers $headers -Body $chatBody -ContentType application/json
Write-Host "Conversation ID:" $chat.conversation_id
Write-Host "Response:" $chat.content

# Continue the conversation
$convId = $chat.conversation_id
$chatBody2 = "{`"message`":`"How many sick days have I used?`",`"conversation_id`":`"$convId`"}"
$chat2 = Invoke-RestMethod -Uri http://127.0.0.1:8000/api/v1/chat -Method POST -Headers $headers -Body $chatBody2 -ContentType application/json
Write-Host $chat2.content

# List all conversations
$convs = Invoke-RestMethod -Uri http://127.0.0.1:8000/api/v1/chat/conversations -Method GET -Headers $headers
Write-Host "Total conversations:" $convs.total

# Read message history
$msgs = Invoke-RestMethod -Uri "http://127.0.0.1:8000/api/v1/chat/conversations/$convId/messages" -Method GET -Headers $headers
$msgs.messages | ForEach-Object { Write-Host "[$($_.role)]" $_.content }

# Delete the conversation
Invoke-RestMethod -Uri "http://127.0.0.1:8000/api/v1/chat/conversations/$convId" -Method DELETE -Headers $headers
Write-Host "Conversation deleted."
```

## 9. Phase 6 Context Summarization Architecture

When a conversation exceeds `CHAT_SUMMARIZATION_THRESHOLD_TURNS` (default: 10 dialogue turns / 20 messages), the background `ContextSummarizer` generates a condensed factual summary stored in `conversation_summaries`.

This historical summary is prepended to subsequent LLM context calls while maintaining the recent sliding window (`CHAT_MAX_HISTORY_TURNS`).

Key Invariants:
1. Summaries are stored separately from operational messages.
2. Summaries are never treated as authorization authority.
3. If summarization fails, the system automatically falls back to the sliding history window.
