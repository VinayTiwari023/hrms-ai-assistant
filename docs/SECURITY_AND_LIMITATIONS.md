# Security Architecture & Operational Limitations

## 1. Architectural Security Philosophy

The **HRMS AI Assistant** implements a strict **Zero-Trust LLM** architecture:

1. **Untrusted Model Layer**: The Large Language Model (LLM) is treated as an untrusted presentation component. The model is never permitted to evaluate permissions, make authorization decisions, or act as an identity authority.
2. **Server-Side Enforcement**: All authorization policies, role verifications, and parameter constraints are enforced strictly server-side by FastAPI dependency injection before tool execution or document retrieval occurs.
3. **Identity Derivation from Cryptographic Claims**: For all employee self-service tools (`get_my_profile`, `get_my_leave_balance`, `get_my_attendance_today`, etc.), the backend ignores any `employee_id` parameter provided by the client or generated by the LLM. The employee identity is bound directly to the cryptographically validated JWT claim (`current_user.employee_id`).
4. **Passive Document Context**: All retrieved company policy chunks and HRMS records are treated as passive factual data. Prompt engineering demarcates retrieved context within strict fences to defend against indirect prompt injection.

## 2. Implemented Security Controls

### 2.1 Cryptographic & Credential Security
- **PBKDF2-HMAC-SHA256**: Compliant with OWASP password storage guidance using 600,000 iterations and 16-byte cryptographically secure random salts.
- **Transparent Hash Auto-Migration**: Outdated hashes are automatically upgraded to 600,000 iterations upon successful user authentication.
- **JWT Lifecycles**: Signed with HS256, strictly validating issuer (`iss`), audience (`aud`), expiration (`exp`), and unique token identifier (`jti`).
- **Session Revocation**: Calling `POST /api/v1/auth/logout` places the token's `jti` into an in-memory token blacklist, immediately rejecting subsequent calls with `401 Unauthorized`.

### 2.2 Abuse Mitigation & Invariant Defense
- **Brute Force Protection**: Sliding-window rate limiting on login attempts (5 failed attempts trigger a 300-second lockout).
- **User Enumeration Defense**: Uniform `401 Unauthorized` responses with identical error messages for nonexistent accounts and incorrect passwords.
- **Production Secret Validation**: In `production` and `staging` modes, weak secrets (< 32 chars), common words (`secret`, `password`, `admin`), and placeholder strings are rejected at startup.
- **Wildcard CORS Defense**: Wildcard origin `*` is strictly rejected when credentialed requests are allowed.

### 2.3 RAG Knowledge Isolation
- **Multi-Level Role Filtering**: Knowledge documents and vector retrieval enforce 4 access tiers (`public`, `employee`, `hr`, `admin`).
- **Department Boundary Enforcement**: Documents classified for specific departments (e.g. `Engineering`, `Finance`) are isolated to employees of that department; standard cross-department queries receive zero chunks.
- **Defense-in-Depth Verification**: Vector database query filtering is mirrored by post-retrieval verification before chunks are formatted into system context.

## 3. Current Operational Limitations

To maintain accurate positioning for enterprise architects and open-source adopters, the following limitations are explicitly documented:

| Feature / Area | Current Status | Production Implication |
| :--- | :--- | :--- |
| **HRMS Sample Data** | **Fictional Only** | All sample employees and policies represent the fictional entity **NovaTech Innovations**. |
| **Mock HRMS Adapter** | **Development/Testing Only** | Production and staging environments strictly reject `MockHRMSAdapter`. A real enterprise HRMS API must be configured via `HttpHRMSAdapter` or a custom adapter. |
| **Public Registration** | **Disabled in Production** | `ALLOW_PUBLIC_REGISTRATION=false` by default in production. |
| **Email Verification** | **Not Implemented** | Email ownership verification (SMTP challenge/confirmation links) is not yet implemented. In production, employee accounts should be provisioned via admin APIs or enterprise identity federation. |
| **Enterprise SSO / SAML / OIDC** | **Not Implemented** | Native SAML 2.0 or OIDC SSO flows are not currently built into the application. Deployments must use an API Gateway / Reverse Proxy (e.g. OAuth2-Proxy, Keycloak, Okta) to terminate enterprise SSO and map identity claims into Bearer JWTs. |
| **HRMS Mutations (Write Operations)** | **Disabled** | All tool operations that write or mutate HRMS records (leave booking, punches, profile edits) remain gated behind `HRMS_MUTATIONS_ENABLED=false`. |
| **Inference Hardware Requirements** | **GPU Recommended** | Local inference on CPU-only hardware suffers significant latency (~69–113 s TTFT). Production deployments require dedicated GPU nodes (Ollama, vLLM, or TGI). |
| **Persistence Clustering** | **Single-Node SQLite WAL** | The current metadata and conversation storage uses SQLite in WAL mode. For multi-replica horizontal clustering, a distributed database backend (e.g. PostgreSQL) is required. |
